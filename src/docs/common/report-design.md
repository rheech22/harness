# 리포트 HTML 디자인

## 적용 범위

이 문서는 HTML 리포트에 적용되는 디자인을 안내합니다. Markdown 문서는 대상이 아닙니다. 본문 문체와 용어는 [산문 문체 기준](prose-style.md), 저장소 문서의 제목과 구조는 문서 작성 기준이 소유합니다. 제품 화면의 디자인 토큰은 프로젝트의 디자인 시스템 문서이 소유하며 이 문서와 공유하지 않습니다.

## 배경

HTML 리포트를 요청하면 에이전트마다 각기 다른 양식으로 결과를 만듭니다. 가령 '브루탈리즘'이라는 키워드를 언급해도 요청이 충분히 구체적이지 않아 불필요한 요소가 화면을 채우는 경우가 잦았습니다. 그 결과 가독성이 떨어졌습니다. 코드 리뷰와 기능 설명 등 서로 다른 목적의 리포트 생성 Skill이 추가될 때마다 디자인을 반복해서 서술하지 않고 함께 참조할 기준도 필요했습니다.

- 화면을 불필요한 요소로 채우지 않습니다.
- 가독성을 해치지 않아야 합니다.
- 구획은 여백과 배경 대비로 만듭니다.
- 색은 종이, 잉크, 강조 이렇게 셋입니다. 강조가 하나뿐이면 그 색이 나타날 때 실제로 강조로 읽힙니다. 단, 특별한 목적이 있다면 색을 더 사용할 수도 있습니다. (예: 퀴즈의 정답, 오답 표기 색상)
- 위계 또한 가급적 크기가 아니라 여백으로 구성합니다. 제목을 키우는 것은 목록을 읽을 때 도움이 되지만 문단을 읽을 때는 방해가 됩니다. 리포트는 훑는 문서가 아니라 읽는 문서입니다.

## 조립

리포트는 [`report-shell.html`](../../assets/report/report-shell.html)을 복사해 만듭니다. 이 쉘은 팔레트, 타이포, 카드 레이아웃, 표제 블록, 테마 토글, 맨 위로 버튼, 인쇄 규칙과 아래 조판 단위를 담습니다.

본문과 리포트 고유 스타일·스크립트는 세 표시 주석 구간의 내용만 통째로 바꿉니다. 표시 주석 자체는 남깁니다. 표시 주석을 보존하면 구간 구조를 검사할 수 있지만, 공유 쉘과 수정하지 않은 부분이 같은지는 별도로 확인해야 합니다.

| 구간     | 표시 주석                                                 | 내용                        |
| ---      | ---                                                       | ---                         |
| 스타일   | `/* BODY_STYLE:start */` … `/* BODY_STYLE:end */`         | 이 리포트에만 있는 스타일   |
| 본문     | `<!-- BODY:start -->` … `<!-- BODY:end -->`               | 본문 마크업                 |
| 스크립트 | `<!-- BODY_SCRIPT:start -->` … `<!-- BODY_SCRIPT:end -->` | 이 리포트에만 있는 스크립트 |


표제의 <span v-pre>`{{TITLE}}`</span>, <span v-pre>`{{KICKER}}`</span>, <span v-pre>`{{HEADING}}`</span>과 메타 행은 리포트마다 채웁니다. 메타의 개수와 항목은 각 리포트 가이드가 정하며, 메타 행을 두지 않는 리포트는 `<dl>`을 통째로 지웁니다.

쉘이 제공하는 조판 단위는 다음과 같습니다. 무언가를 새로 만들기 전에 먼저 살펴야 합니다.

| 단위 | 용도 |
| --- | --- |
| `.lbl` | 절 라벨. 고정폭 글꼴 10px |
| `.explanation` + `.section-title` | 기술 설명 전용 16px 본문과 18px 절 제목. 실제 `h2`를 사용합니다 |
| `.h3` | 절 안의 소제목. 라벨과 문서 제목 사이의 한 층 |
| `.toc` | 목차 |
| `.note` | 콜아웃 |
| `.diagram` | 노드 넷 이하의 단순한 가로 흐름 |
| `.diagram.stack` | 노드가 다섯 개 이상이고 분기와 연결선 라벨이 없는 세로 흐름 |
| `.viz`, `.viz-breakout` | 구조가 필요한 인라인 SVG와 본문 읽는 폭을 벗어나 카드 안쪽까지 넓히는 다이어그램 |
| `.box`, `.box.dim` | 다이어그램 노드 |
| `details` | 건너뛸 수 있는 설명 |
| `figure.code` + `pre[data-hl]` | 코드 스니펫과 줄 강조 |
| `pre.out` | 실행 출력 |
| `.tbl` | 표. 격자선 없이 정렬과 여백으로 열을 나누고, 넓어지면 자기 안에서 가로로 스크롤합니다 |
| `code`, `.path` | 인라인 코드와 경로 표기 |
| `.col`, `.wide` | 36rem과 42rem 읽는 폭 |
| `.ok`, `.bad` | 퀴즈의 정답과 오답 |


스니펫 두 개가 한 지적의 근거이면 새 스타일을 만들지 말고 `.lbl` 한 줄을 단 `div`로 묶습니다.

일반적인 본문 흐름은 다음 세로 간격을 기본값으로 씁니다.

| 자리 | 값 | 소유자 |
| --- | --- | --- |
| 문단 사이 | `.9rem` | 공유 쉘 |
| 블록 위아래(코드, 출력, 콜아웃, 목차, 접힘, 다이어그램, 표) | `1.25rem` | 공유 쉘 |
| 반복되는 독립 항목 사이 | `2.5rem` 이상 | 리포트별 template |

공유 쉘의 일반 블록 값은 대칭이라 인접한 여백이 겹쳐서 커지지 않습니다. 이 블록들의 `margin`을 리포트에서 다시 정하지 않아야 합니다.

컴포넌트 내부와 리포트 구조의 간격은 예외입니다. 공유 쉘은 표제, 구분선, 라벨, 소제목처럼 역할이 정해진 컴포넌트에 별도 간격을 둡니다. 리포트별 template도 발견 항목, 지적과 제안 구획, 선택지, 꼬리 절처럼 구조를 나타내는 간격을 `BODY_STYLE`에서 정의할 수 있습니다. 이 값은 해당 컴포넌트나 template이 소유하며, 산출물마다 다시 고르지 않고 canonical template을 그대로 따릅니다. 새 구조에 간격이 필요하면 일반 본문 흐름과 다른 이유를 확인한 뒤 해당 리포트 template이나 가이드에 정의합니다.

이 허용은 자기 template을 가진 리포트에만 적용합니다. 기술 설명 아티클의 `BODY_STYLE`은 퀴즈 템플릿의 조각과 정확히 같아야 하며 산출물마다 한 줄도 더하지 않습니다. checker가 두 값을 문자로 대조하므로 여기서 예외를 쓰면 검사에서 막힙니다. 기술 설명에 새 간격이 필요하면 산출물이 아니라 공유 쉘이나 퀴즈 템플릿을 고칩니다.

단순 다이어그램은 한 줄에 노드 넷까지 둡니다. 그보다 길지만 분기가 없다면 `.diagram.stack`을 씁니다. 분기, 경계, 상태 전이, 라벨이 있는 연결선이 필요하면 리포트 SVG 다이어그램에 따라 `.viz`와 인라인 SVG를 사용합니다.

기본 코드 리뷰에서 `figure.code`의 `figcaption`은 저장소에 실재하는 코드일 때만 달고, 독자가 그 경로를 열어볼 수 있어야 합니다. 기술 설명은 예외입니다. 조사 위치를 독자에게 표시하지 않으며 필요한 캡션은 코드의 목적만 짧게 설명합니다. 모든 스니펫에 캡션을 강제하지 않습니다.

코드 블록과 표처럼 축소하면 읽을 수 없는 블록은 자기 안에서 가로로 스크롤해야 합니다. 다이어그램은 예외입니다. `.viz-breakout`으로 본문 읽는 폭을 벗어나 카드 안쪽까지 넓히고, 화면이 좁아지면 SVG 전체를 가용 폭에 맞춰 축소합니다. 표에는 따로 감싸는 `div`가 필요하지 않고 `.tbl`이 스스로 처리합니다.

`.ok`와 `.bad`는 색을 입힐 텍스트에 직접 답니다. 버튼이나 상자 같은 요소에 달면 그 요소의 다른 색 규칙과 겹칩니다.

`data-hl`에는 1부터 센 줄 번호를 적습니다. 여러 줄은 `data-hl="4,5"`처럼 쉼표로만 잇습니다. 파서가 공백을 다듬지 않아 `"4, 5"`는 뒤쪽이 조용히 무시됩니다.

코드에는 실제 소스 언어의 `language-*` 클래스를 명시합니다. 공유 쉘은 Prism 1.29.0과 공식 Dart 문법을 인라인으로 포함하며, Dart가 의존하는 `clike`를 먼저 로드합니다. 새 문법도 공식 버전·의존 순서·라이선스를 보존하고 원격 autoloader를 넣지 않습니다. 기술 설명 checker는 저장소가 소유한 이 번들의 실제 언어 registry만 사용하며 검사 대상 HTML의 스크립트를 실행하지 않습니다. `plain`은 의사 코드나 출력용이며 미지원 언어를 숨기는 대체값이 아닙니다.

줄 강조는 토큰 하이라이트와 별개입니다. 여러 줄 주석·문자열의 토큰을 줄별로 나누더라도 원문과 줄바꿈을 보존합니다. 기존 토큰 색은 유지하되 설명에서는 타입을 강조색 굵게, 함수를 잉크색 굵게, 키워드를 강조색, 문자열을 코드 잉크색, 주석을 흐린색으로 구분합니다. 다른 리포트의 토큰 스타일은 바꾸지 않습니다.

쉘 파일 자체가 명세서입니다. 브라우저로 열면 본문 자리에 조판 단위가 하나씩 예시로 들어 있어, 새 리포트를 만들기 전에 무엇이 이미 있는지 눈으로 확인할 수 있습니다.

구조가 반복되는 리포트는 본문 조각을 템플릿 파일로 둡니다. [코드 리뷰 리포트 본문](../../assets/report/code-review-report.html.template)이 그 예입니다. 매번 구조가 달라지는 리포트는 템플릿 대신 해당 가이드가 절 구성을 정합니다.

### 기술 설명의 읽기 조판

기술 설명은 `BODY` 안의 `.explanation`으로 조판을 선택합니다. 공유 쉘의 기본 본문, 표제와 코드 리뷰 탭에는 적용하지 않습니다. 읽는 폭은 36rem, 본문은 16px/1.85이며 좁은 화면에서도 본문 글자를 줄이지 않습니다. 다이어그램은 기존 `.viz-breakout`으로 넓힐 수 있습니다.

절 제목은 잉크색 18px `h2.section-title`, 하위 제목은 16px `h3.h3`를 사용합니다. `.lbl.m`은 목차 안내나 메타 라벨에 남기고 절 제목으로 쓰지 않습니다. 큰 제목 단계를 늘리는 대신 절 사이 3.5rem, 절 제목 아래 1.25rem, 소제목 위 2rem으로 독서 단위를 구분합니다. 일반 문단과 블록 간격은 공유 기본값을 유지합니다.

설명 안의 인라인 코드는 13px, 표와 목차는 14px입니다. 코드 블록은 공유 크기와 가로 스크롤을 유지합니다. commit hash, Git range, 저장소 경로와 줄 번호는 메타·캡션·접힌 설명·퀴즈 어디에도 노출하지 않습니다. 원본 대조 자료는 생성기 내부에 보관하고 의미 있는 identifier, 필요한 버전과 공식 출처 link는 남깁니다.

목차 블록은 내용에 맞는 폭으로 가운데에 두되 본문보다 넓어지지 않게 제한합니다. `목차` 제목은 가운데 정렬한 강조색이고, 항목은 왼쪽 정렬입니다. 번호 폭을 일정하게 두어 긴 항목의 다음 줄도 제목 시작 위치에 맞춥니다. 표제는 별도 구획으로 유지하며 퀴즈를 목차에 추가하지 않습니다.

설명 아티클은 700px 이하 화면에서 테마 버튼을 페이지 앞의 도구 영역에, 맨 위로 버튼을 글 끝에 배치합니다. 두 버튼 모두 문서 흐름 안에 두어 본문이나 선택지를 덮지 않으며, 본문 가로 폭은 줄이지 않습니다. 테마 버튼의 DOM 읽기 순서도 페이지 앞에 맞춥니다. 코드 리뷰에도 같은 모바일 배치를 적용합니다. 넓은 화면과 그 밖의 보고서는 기존 고정 배치를 유지하고, 인쇄에서는 컨트롤을 숨깁니다.

접힌 설명은 닫혔을 때와 열렸을 때 같은 중립색 컨테이너를 사용합니다. 옅은 배경과 안쪽 여백으로 열린 내용의 시작과 끝을 구분하며, 외곽선·summary 구분선·그림자·대체 측면선은 쓰지 않습니다. 넉넉한 summary 영역 전체를 누를 수 있게 하고 네이티브 `details`·`summary`, 화살표 상태와 키보드 포커스 outline을 유지합니다. 자동으로 열거나 닫지 않으며 열린 내용을 인쇄에서도 유지합니다. 코드의 자체 스크롤, 표의 줄바꿈과 SVG의 컨테이너 맞춤으로 넘침을 처리하며, 내용을 잘라 숨기지 않습니다. 강조색 퀴즈와는 색조로 구분하고 중첩 `details`는 쓰지 않습니다.

설명 전용 표는 중립적인 옅은 헤더 배경, 잉크색 중간 굵기와 2px 아래 구분선으로 제목 행을 구분합니다. 본문 행에는 1px 가로 구분선과 넉넉한 셀 안쪽 여백을 두고 세로 격자는 쓰지 않습니다. 첫 열은 비교 대상이나 조건을 명명하고, 행 제목이면 `th scope="row"`를 사용합니다. 고정 표 레이아웃 안에서 긴 셀과 identifier를 줄바꿈해 모바일 페이지 폭을 넘지 않게 합니다. 코드 리뷰의 대안 비교 표에도 같은 조판을 적용합니다. 그 밖의 리포트 표에는 적용하지 않습니다.

순서가 중요한 절차는 `ol.narrative-list`, 같은 종류의 조건·이벤트는 `ul.narrative-list`로 표시합니다. 두 종류 모두 `::marker`를 `--accent`로 칠하며, 읽을 수 있는 들여쓰기와 항목 간격을 유지합니다. 이 클래스는 목차와 퀴즈에 사용하지 않습니다. 평행한 짧은 구절과 종결 마침표 생략은 기술 설명 목록 항목만의 예외이며, 설명 문장의 공통 문체는 바꾸지 않습니다. 비교는 표, 인과와 해석은 산문을 사용하고 내용을 중복하지 않습니다.

문항별 퀴즈는 관련 전개 위치에서 처음부터 보입니다. 옅은 강조색 배경과 작은 강조색 라벨, 읽기 쉬운 질문·버튼으로 구분합니다. 목차·결말의 퀴즈, 열기 토글, 점수와 읽기 제한은 없습니다. 퀴즈 데이터와 접근성 계약은 [HTML 리포트 생성](html-report.md#퀴즈)이 정합니다. 표·목록의 값은 공유 쉘, 퀴즈 내부 조판은 퀴즈 템플릿이 소유하므로 산출물마다 다시 고르지 않습니다.

### 코드 리뷰의 읽기 조판

코드 리뷰는 본문 전체를 `.code-review`로 감싸 읽기 조판을 선택합니다. 본문은 16px/1.85이고 인라인 코드와 경로는 각각 13px와 12px입니다. 결과·검증 기록 탭은 읽기 쉬운 본문 크기로 표시합니다. 중요도는 각 지적에 항상 표시합니다. 지적과 꼬리 절의 제목은 18px, 문제·제안 구획은 실제 `h3`와 16px를 사용합니다. 지적의 읽는 폭과 간격은 [코드 리뷰 본문 템플릿](../../assets/report/code-review-report.html.template)이 소유합니다.

표, 접힌 설명, `narrative-list`와 모바일 버튼은 기술 설명의 읽기 조판과 같은 공유 스타일을 사용합니다. 검증 기록의 접힌 설명만 배경을 비우고 얇은 테두리를 둘러 반복 항목의 클릭 영역을 구분합니다. 코드 리뷰의 본문에 `.explanation`을 붙이거나 설명용 목차·퀴즈·코드 강조 규칙을 가져오지 않습니다. 경로와 줄 번호는 근거를 확인하는 데 필요하므로 그대로 표시합니다.

지적의 영향, 판단에 필요한 근거 요약·한계, 권장 제안과 미해결 결정은 결과 화면에 펼쳐 둡니다. 코드 스니펫, 재현 절차와 상세 출력은 각 지적의 `details`에 기본 접힘으로 둡니다. 상세 근거를 읽지 않아도 무엇이 문제이고 어떻게 고칠지 이해할 수 있어야 합니다.

리뷰 결과는 중요도순으로 한 화면에 표시하고 검증 기록은 별도 탭에서만 표시합니다. 표제 외의 내용을 탭 밖에 붙이지 않습니다. 검증 기록은 절 사이의 얇은 구분선과 일정한 간격으로 묶습니다. 검사별 상태·이름·결과를 행으로 나누고 좁은 화면에서는 상태를 위로 쌓습니다. 상태는 글자로 구분하며, 미확인 범위는 접지 않습니다. 제외 근거와 경로 대조는 요약이 있는 펼침으로 둡니다. 검증 기록의 범위와 생략할 내부 정보는 코드 리뷰 가이드의 HTML 리포트 계약을 따릅니다.

복수 제안의 조건과 득실을 비교해야 할 때만 `table.tbl`을 사용합니다. 표에는 caption과 열 제목을 두고 행 제목에는 `scope="row"`를 씁니다. 같은 득실을 표와 목록에 반복하지 않습니다. 짧은 제안은 문단으로 유지하고, 재현 순서는 `ol.narrative-list`로 표현할 수 있습니다. 다이어그램은 실패 경로나 의존 관계를 이해하는 데 필요할 때만 리포트 SVG 다이어그램을 따릅니다.

## 규칙

각 규칙에 이유를 답니다. 이유를 읽고도 지금 상황에 맞지 않는다고 판단하면 규칙을 고치고 이 문서를 갱신합니다. 산출물에서 조용히 어기지 않아야 합니다.

### 구획을 선으로 나누지 않습니다

절과 절, 항목과 항목을 가르는 수단은 여백과 가운데 정렬한 구분선입니다. 기본 표는 정렬과 여백으로 열을 구분합니다. 기술 설명과 코드 리뷰의 비교 표에만 위 조판에 따른 얇은 가로 구분선을 사용하며 세로 격자는 추가하지 않습니다.

검증 기록은 검사 결과를 행 단위로 비교하므로 절과 검사 행 사이의 얇은 가로선, 상태 라벨과 펼침의 테두리를 허용합니다. 이 예외는 리뷰 결과 본문에는 적용하지 않습니다.

위 읽기 조판 표와 검증 기록의 예외를 제외하면 선은 콜아웃(`.note`)과 다이어그램 요소에 사용합니다. `.note`와 단순 `.box`는 면을 칠하지 않고 강조색 테두리 1px만 씁니다. 구조화된 SVG의 중심 노드와 경계는 리포트 SVG 다이어그램의 옅은 색조 면을 사용할 수 있습니다. 이 요소들은 본문 흐름을 가르지 않고 흐름 안에서 한 덩어리를 분리하므로 선이 제 역할을 합니다.

이유: 코드 블록이 이미 큰 면을 차지하므로 구획마다 선을 더하면 불필요한 구획선으로 느껴집니다. 선은 최소한으로 사용합니다.

### 색은 셋이고 강조는 한 모드에 하나입니다

종이, 잉크, 강조뿐입니다. 심각도, 링크, 선택된 탭, 강조한 코드 줄이 모두 같은 강조색을 씁니다. 다이어그램의 단색 계열 팔레트도 새 색상을 추가하지 않고 모드별 강조색에서 파생합니다.

이유: 강조가 둘 이상이면 어느 쪽이 더 중요한지 색만으로 판단할 수 없습니다. 색을 늘리는 대신 밝기로 층을 나눕니다.

### 면을 칠하지 않습니다

배지와 라벨에 배경색을 깔지 않고 글자색으로만 구분합니다. 심각도는 강조색, 잉크색, 흐린색 셋으로 나타냅니다. 다이어그램의 중심과 경계는 관계를 따라가는 데 필요한 범위에서만 옅은 색조 면을 사용합니다. 기술 설명과 코드 리뷰의 표 헤더·접힌 설명, 기술 설명의 분산 퀴즈는 읽는 역할을 구분하기 위한 옅은 배경의 예외이며, 새 색상을 도입하지 않습니다.

이유: 칠한 배지는 읽기 전에 눈을 끕니다. 한 화면에 열 개가 나오면 본문이 배경으로 밀립니다.

### 위계는 크기가 아니라 여백으로 만듭니다

기본 리포트의 본문 위 제목은 15px를 넘기지 않고 굵기와 위 여백으로 구분합니다. 문서 제목은 28px를 씁니다. 기술 설명과 코드 리뷰는 위 읽기 조판의 18px 제목과 16px 하위 제목을 예외로 사용합니다. 긴 글의 제목이 10px 메타 정보처럼 보이지 않게 하면서 크기 단계를 제한합니다.

이유: 크기로 위계를 만들면 화면이 요란해지고, 절이 늘어날수록 크기 단계를 더 만들어야 합니다. 여백은 단계를 늘려도 조용합니다.

### 굵게는 식별자에만 사용합니다

코드 안에서 함수와 컴포넌트 이름, 그리고 절 제목에만 굵기를 줍니다. 본문 문장에는 쓰지 않습니다.

이유: 굵은 글자가 문장 안에 섞이면 읽는 흐름이 끊깁니다. 강조가 필요하면 문장을 다시 씁니다.

### 색과 여백을 직접 적지 않습니다

쉘이 정의한 변수만 씁니다. 산출물의 `BODY_STYLE`에 색 리터럴을 적지 않아야 합니다. 블록 사이 여백도 쉘이 정한 세 값을 그대로 씁니다.

이유: 쉘의 팔레트는 `light-dark()`로 라이트와 다크 값을 함께 들고 있습니다. 리터럴을 적으면 그 자리만 테마를 따라가지 못합니다. 여백을 각자 정하면 리포트마다 리듬이 달라지고, 블록 뒤 본문이 붙어 보이는 일이 생깁니다.

### 쉘 구간을 고치지 않습니다

복사본에서 쉘 쪽 CSS나 스크립트를 손대지 않습니다. 바꿀 필요가 있으면 쉘을 고치고 이 문서를 갱신합니다.

이유: 복사본을 고치면 다음 리포트가 서로 다른 기준을 갖게 되고, 어느 쪽이 맞는지 판단할 근거가 사라집니다.

### 외부 요청을 만들지 않습니다

폰트, CDN, 이미지, 네트워크 호출처럼 자동으로 원격 자원을 로드하는 요소를 넣지 않습니다. 필요한 것은 전부 파일 안에 둡니다. 사용자가 눌러 이동하는 공식 출처의 일반 `a href="https://..."` link는 허용합니다. preload·prefetch·ping이나 클릭을 대신하는 스크립트는 허용하지 않습니다.

이유: 산출물은 `file://`로 열리고 오프라인에서도 읽힙니다. 문법 하이라이터를 CDN 링크 대신 인라인으로 둔 이유도 같습니다.

### 다이어그램은 공유 쉘 조판 단위와 인라인 SVG로 구성합니다

Mermaid와 ASCII 다이어그램을 쓰지 않습니다. 노드 넷 이하의 단순한 흐름은 `.box`와 `.arrow`를 사용합니다. 공간 배치가 필요한 관계는 인라인 SVG로 구성하고 리포트 SVG 다이어그램의 단색 계열 팔레트와 시각 문법을 따릅니다.

이유: Mermaid는 외부 스크립트가 필요해 위 규칙과 충돌합니다. ASCII는 폭이 좁은 화면에서 깨집니다. 인라인 SVG는 공유 쉘의 라이트/다크 모드 토큰을 사용하면서 분기와 경계를 정확하게 배치할 수 있습니다.

## 문체

리포트 본문의 문체와 용어는 [산문 문체 기준](prose-style.md)이 소유합니다. 그 문서의 적용 범위가 리포트를 포함하므로 본문 작성 원칙, 문체·용어 기준과 AI 문체 패턴 표를 그대로 따르고 여기서 항목을 다시 나열하지 않습니다.

리포트에만 적용하는 차이는 둘입니다. 산출물은 저장소 문서가 아니므로 frontmatter와 문서 타입 규칙을 따르지 않습니다. 그리고 확정되지 않은 판단은 단정하지 않고 무엇을 확인하지 못했는지 함께 적습니다. 리뷰와 설명은 근거의 강도가 항목마다 다르기 때문입니다.

## 예외

- 코드 블록과 인라인 코드는 배경을 씁니다. 코드와 문장의 경계를 폰트만으로 구분하면 한글 본문 안에서 잘 보이지 않습니다.
- 강조색은 모드마다 다릅니다. 라이트는 코발트 `#103dff`, 다크는 노랑 `#f0c14b`입니다. 코발트를 명도만 올려 다크에 쓰면 성격이 옅어져 평범한 파랑이 됩니다.
- 강조한 코드 줄의 배경은 6%를 넘기지 않습니다. 다크에서 노랑을 더 진하게 깔면 회색 코드 바탕 위에서 올리브빛으로 탁해집니다.
- 퀴즈의 정답과 오답에만 `--ok`와 `--bad`를 씁니다. 강조색 하나로는 맞고 틀림을 구분할 수 없습니다. 이 두 색은 다른 자리에 쓰지 않습니다.
- 리포트에 따라 최상위 구조가 다릅니다. 코드 리뷰는 결과와 검증 기록을 탭으로 나누고 기술 설명은 도입, 가변 중간 절, 결말을 순서대로 읽습니다. 기술 설명의 연습 문항은 관련 전개 지점에서 건너뛸 수 있게 배치합니다. 발견 목록은 골라 보는 대상이고 설명은 읽는 순서가 있기 때문입니다.

## 검증

산출물을 저장하기 직전에 세 가지를 확인합니다. 산출물이 저장소 밖에 생기므로 CI가 대신 잡아 주지 않습니다.

```bash
rg -n "src\\s*=\\s*[\"']https?:|<link[^>]*href\\s*=\\s*[\"']https?:|url\\(\\s*[\"']?https?:|@import\\s+(url\\(\\s*)?[\"']?https?:" <파일>
for marker in BODY_STYLE:start BODY_STYLE:end BODY:start BODY:end BODY_SCRIPT:start BODY_SCRIPT:end; do
  test "$(rg -F -c "$marker" <파일>)" -eq 1 || exit 1
done
perl -0777 -ne 'print $1 if m{/\* BODY_STYLE:start \*/(.*?)/\* BODY_STYLE:end \*/}s' <파일> \
  | rg -n '#(?:[0-9a-fA-F]{3,4}|[0-9a-fA-F]{6}|[0-9a-fA-F]{8})\b'
```

첫 번째는 0건이어야 합니다. `http`를 통째로 세지 않는 이유는 쉘이 인라인한 Prism license 주석에 URL이 들어 있어 규격대로 만든 산출물도 걸리기 때문입니다. 요청을 만드는 참조만 셉니다.

두 번째는 명령이 성공해야 합니다. 여섯 표시 주석이 각각 정확히 한 번 있어야 합니다. 이 검사는 구간 구조만 확인하므로, 쉘에서 표시 구간 밖을 고치지 않았는지는 생성 과정이나 원본 대조로 확인합니다.

세 번째는 0건이어야 합니다. `BODY_STYLE`에 색 리터럴이 있으면 쉘의 변수로 바꿉니다. 0건일 때 `rg`가 종료 코드 1을 반환하는 것은 정상입니다.

휴대폰에서 읽는 경우도 고려하여 좁은 폭도 확인합니다. 393px 폭에서 페이지와 다이어그램에 좌우 스크롤이 없어야 합니다. 다이어그램은 카드 안쪽 폭을 넘지 않고 가용 폭에 맞춰 축소되어야 합니다. 다이어그램의 추가 검증은 리포트 SVG 다이어그램을 따릅니다.

본문을 다 쓴 뒤에는 위 문체 절의 항목으로 한 번 훑습니다. 이중 피동, 결산 상투구, 과장 어휘, 대명사 남용이 가장 자주 남습니다.

쉘 자체를 고쳤다면 [`report-shell.html`](../../assets/report/report-shell.html)을 브라우저로 열어 조판 단위가 모두 보이는지, 테마 토글이 양쪽으로 동작하는지 확인합니다.

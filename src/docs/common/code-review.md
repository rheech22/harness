# 코드 리뷰 워크플로우

## 목표

코드 변경을 프로젝트의 source of truth와 대조하고 자동 검사가 잡지 못하는 결함을 찾습니다. 이 워크플로우는 리뷰만 수행하며 코드를 수정하지 않습니다. 지적 사항을 보고하고 무엇을 바꿀지는 사용자가 결정합니다.

이 문서는 절차와 품질 기준을 정의하고 프로젝트마다 달라지는 값은 정하지 않습니다. base ref, 자동 검사 목록, 관점별 기준 문서, 전체 검사 명령, 리포트 저장 경로는 [프로젝트 프로필](profiles/code-review.default.md)이 정합니다. 절차를 따르다 프로필을 가리키는 자리를 만나면 그 문서에서 값을 읽습니다. 프로젝트에 프로필이 없으면 기본값을 씁니다.

## 리뷰 범위

기본 대상은 현재 branch와 base 사이의 commit diff에 작업 트리와 index의 변경을 더한 범위입니다. 아직 commit하지 않은 변경도 리뷰에서 빠뜨리지 않습니다. base ref는 프로필이 정합니다.

```bash
git diff <base>...HEAD --stat
git diff --stat
git diff --cached --stat
```

사용자가 다른 범위, directory, 파일을 지정하면 그 범위를 사용합니다. 기본 범위에서는 세 명령의 파일 목록을 합쳐 중복을 제거합니다. 판단하기 전에 staged, unstaged, commit diff를 모두 읽습니다. 지적 사항이 diff 밖의 동작에 의존하면 관련 주변 코드도 읽습니다.

## 자동 검사와의 경계

CI나 린터가 이미 강제하는 항목을 지적 사항으로 반복하지 않습니다. 무엇이 강제되는지는 프로필의 자동 검사 표가 정합니다. 변경이 그 검사 중 하나에 실패할 것이 분명하면 한 줄로만 알리고 항목별 지적 사항으로 나열하지 않습니다. 프로필이 "자동 검사 보장이 없다"고 밝힌 영역에서는 작성자가 검사를 실행했는지 확인하고 자동 실행됐다고 가정하지 않습니다.

## 리뷰 관점

diff가 건드린 관점만 기준 문서에 대조합니다. 적용할 수 없는 관점은 조사하지 않되 검증 기록에 건너뛴 이유를 남깁니다. 관점 9는 예외이며 diff 종류와 무관하게 항상 실행합니다. 이벤트 누락은 정의상 diff에 흔적을 남기지 않기 때문입니다. 규칙을 기억에 의존해 재구성하지 않고 기준 문서를 실제로 읽습니다. 관점별 기준 문서는 프로필이 지정하며, 프로필이 문서를 지정하지 않은 관점은 이 문서의 일반 기준만으로 판단합니다.

| # | 관점 | 짧은 라벨 | 검토 책임 |
|---|---|---|---|
| 1 | 코드 스타일 판단 | 코드 스타일 | 자동화하기 어려운 판단을 프로젝트의 코딩 스타일 문서에 대조합니다. |
| 2 | 프로젝트 고유 금지 규칙 | 금지 규칙 | lint가 아직 강제하지 않는 프로젝트 규칙(예: 번역 key 규칙)을 프로필이 지정한 문서에 대조합니다. |
| 3 | 아키텍처 경계 | 경계 | 린터가 다루지 않는 layer 배치, cross-import 전략, migration 예외, naming 판단을 프로젝트의 아키텍처 문서에 대조합니다. |
| 4 | UI 품질 | UI 품질 | 스타일 구성, 토큰, touch-safe interaction을 프로젝트의 UI 규칙 문서에 대조합니다. |
| 5 | 누락된 문서 갱신 | 문서 동기화 | 변경 trigger에 해당하는 책임 문서가 함께 바뀌지 않았다면 지적 사항으로 보고합니다. trigger 목록은 프로필이 지정한 문서가 정합니다. |
| 6 | 테스트 공백 | 테스트 | 커버리지 수치보다 조용히 회귀할 수 있는 변경 동작에 테스트가 있는지 판단합니다. 변경 동작을 보호한다는 근거로 삼은 테스트와 실패 시나리오는 관점 11에 전달합니다. 관점 11의 확인 없이 테스트 존재만으로 공백이 없다고 결론내리지 않습니다. |
| 7 | 정확성과 실패 처리 | 정확성 | 입력이나 상태가 만드는 구체적인 오동작을 찾습니다. exception, async, cleanup, race, boundary/null, mutation/cache를 확인합니다. |
| 8 | 보안 | 보안 | diff가 새로 만든 취약점을 찾습니다. 프로젝트의 보안 규칙 문서를 따릅니다. |
| 9 | 계측 누락 | 계측 | 새 경로나 대체 경로가 보내야 할 이벤트를 빠뜨렸는지 확인합니다. 퍼널 정의와 이벤트 계약은 프로필이 지정한 문서가 정합니다. 프로필이 계측 문서를 지정하지 않으면 이 관점은 "해당 없음"으로 기록합니다. |
| 10 | 접근성 | a11y | 키보드로 닿고 누를 수 있는지, 포커스가 보이고 옳은 자리로 가는지, 보조기술이 이름·role·상태를 읽는지 확인합니다. 규칙과 예외는 프로젝트의 접근성 기준 문서를 따릅니다. |
| 11 | 테스트 신뢰도 | 테스트 신뢰도 | 추가·변경한 테스트와 이번 변경의 안전성 근거로 인용한 기존 테스트가 틀린 구현에서 실패하는지 확인합니다. 단언·분기·기대값·경계값은 프로젝트의 테스트 작성 기준을 따릅니다. |

관점 문서끼리 충돌하면 프로젝트의 코딩 스타일 문서를 우선하되, 충돌 자체를 보고하고 임의로 한쪽을 선택해 숨기지 않습니다.

관점 7에서는 다음 실패 패턴을 구체적인 시나리오로 검토합니다.

- 삼켜진 exception, 빈 catch, 실패한 뒤에도 사용자에게 실패 상태가 드러나지 않는 경로
- 빠진 `await`, 처리되지 않은 promise rejection, cleanup 누락, race를 허용하는 실행 순서
- 타입이 제한하지 못하는 boundary와 null 처리
- 상태를 제자리에서 바꾸는 mutation, write 뒤 stale한 cache

관점 9는 다음 순서로 대조합니다.

1. diff가 닿는 퍼널 단계를 정합니다.
2. 같은 목적의 기존 경로를 찾아 그 경로가 보내는 이벤트 집합을 뽑습니다.
3. 새 경로에서 빠진 이벤트를 지적 사항으로 보고합니다.

대응 경로가 없는 신규 기능이면 퍼널 단계 정의를 기준으로 판단합니다. 국가나 플랫폼이 갈리는 인증 흐름처럼 같은 목적을 다른 구현으로 제공하는 경로가 이 대조에서 가장 자주 누락됩니다.

관점 10에서는 자동 검사와 타입 검사가 모두 통과해도 남는 다음 결함을 확인합니다. 접근성을 위해 포인터·터치 결과나 화면 모양을 바꾼 diff는 그 자체를 지적 사항으로 보고합니다. 프로젝트 고유 overlay 규칙과 테스트 태그는 프로필이 보탭니다.

- 접근성 lint 규칙을 `eslint-disable`로 끈 줄은 이유가 타당한지 확인합니다. `li`나 `div`에 `onClick`만 다는 우회는 탭으로 닿지 않고 Enter로도 눌리지 않습니다.
- 탭으로 닿은 요소에 포커스 표시가 실제로 보이는지 확인합니다. `opacity: 0`으로 덮은 입력이 포커스를 받으면 outline도 함께 투명해져 표시가 사라집니다.
- 포커스 링이 조상의 `overflow`에 잘리지 않는지 확인합니다. 자르는 조상이 스크롤 컨테이너가 아니면 padding과 음수 margin으로 경계를 넓히고, 스크롤 컨테이너이거나 요소가 컨테이너를 꽉 채우면 그 요소의 링을 안쪽으로 돌립니다.
- Escape 처리기가 `event.defaultPrevented`를 먼저 확인하는지 봅니다. 안쪽 popup이 처리한 Escape를 바깥 overlay가 다시 받으면 두 겹이 한 번에 닫힙니다.
- 선택지 묶음에서 화살표 키가 제출이나 페이지 이동을 일으키지 않는지 확인합니다.

런타임 동작을 주장할 때는 근거 계약에 따라 실제 측정을 인용합니다. 링이 잘린다는 주장에는 요소와 자르는 조상의 경계 좌표를, 탭이 닿지 않는다는 주장에는 탭 순서 관찰을 함께 둡니다.

관점 11은 추가·변경한 테스트와 안전성 근거로 인용한 기존 테스트마다 "어떤 틀린 구현이 이 테스트를 통과하는가"를 묻습니다. 그런 구현을 구체적으로 적을 수 있으면 지적 사항입니다. 아래 항목을 확인합니다.

- 기대값을 알 수 있는데 존재·truthy·범위만 확인하는 단언, 인자 없이 호출 여부만 보는 단언
- optional chaining 뒤 부정 matcher, `indexOf` 위치 비교, 빈 컬렉션 순회처럼 대상이 없으면 통과하는 단언
- 테스트 본문의 조건부 return·분기, 예외를 삼키는 `try`/`catch`, 실제 시계·난수에 따라 달라지는 결과
- matcher 없는 reject·throw 단언, 다른 guard가 먼저 거절해도 통과하는 입력
- production과 같은 공식·상수로 만든 기대값, mock 값을 그대로 돌려받는 확인
- 테스트 이름이 약속한 순서·조건을 단언하지 않는 경우
- 수용 쪽 경계값이나 guard별 거절 경로가 빠진 검증 로직 테스트

존재 자체가 검증 대상인 단언처럼 프로젝트의 테스트 작성 기준이 예외로 둔 경우는 보고하지 않습니다.

## 근거 계약

모든 지적 사항은 독자가 반증할 수 있는 근거를 포함해야 합니다.

| 지적 사항 종류 | 필수 근거 |
|---|---|
| 관점 1~6의 규칙 위반 | `file:line`, 문제가 되는 줄을 표시한 코드 스니펫, 기준 규칙 링크 |
| 관점 7의 결함 | `file:line`, 문제가 되는 줄을 표시한 코드 스니펫, 어떤 입력이나 상태가 어떤 잘못된 결과를 만드는지 설명한 실패 시나리오 |
| 런타임 동작 주장 | 실제로 측정한 명령이나 관찰과 그 출력 |
| 관점 11의 약한 테스트 | `file:line`, 문제가 되는 단언을 표시한 코드 스니펫, 그 테스트를 통과하는 구체적인 틀린 구현. 변이로 확인했다면 바꾼 줄과 테스트 결과 |
| 관점 9의 "누락 없음" 결론 | diff가 사용자 경로에 닿으면 퍼널 단계, 대응 경로, 기존 이벤트 집합, 새 경로 이벤트 집합을 담은 대조표. 닿지 않으면 그 사실 한 줄 |

스니펫은 검토한 코드 상태에서 그대로 가져오고 HTML로 이스케이프합니다. Diff 밖의 기존 테스트나 방어 장치를 인용하면 이번 변경과의 관련성을 함께 설명합니다. 판단의 근거가 되는 줄만 남기고 나머지는 `...`으로 줄입니다. 독자가 스니펫만 보고도 무엇이 문제인지 짚을 수 있어야 합니다.

런타임, build step, config가 세션에서 무엇을 load하는지, hook이 언제 실행되는지, glob이 무엇과 일치하는지 같은 주장은 설정을 읽고 추론하지 않습니다. 직접 측정하고 결과를 인용합니다. 어느 근거 형식으로도 뒷받침할 수 없는 의심은 지적 사항에서 제외합니다.

관점 7은 문서 대조보다 추론 비중이 높아 오탐이 생기기 쉽습니다. 결함인지 확신할 수 없으면 지적 사항으로 보고하지 않습니다.

## 절차

1. 리뷰 범위와 파일 목록을 확정합니다. Base와 HEAD의 commit SHA, staged·unstaged diff의 내용 해시를 기록합니다. 범위에 포함한 미추적 파일이 있으면 파일 목록과 내용 해시도 기록합니다.
2. 전체 diff와 필요한 주변 코드를 읽고, 변경 동작의 계약과 합의된 예외를 확인합니다. 적용 관점과 공통 제약을 정하되 결함 여부를 미리 결론내리지 않습니다.
3. 관점별로 기준 문서를 읽고 후보를 독립적으로 찾습니다. 관점 9는 항상 실행합니다.
4. 후보의 근거와 반례를 검증하고 근본 원인별로 정리합니다. 해결책의 상충과 관점 사이의 의존성을 확인한 뒤 필요한 후속 검토만 수행합니다.
5. 시작할 때 기록한 코드 상태와 다시 대조합니다. 달라졌으면 영향을 받은 근거와 결론을 새 상태에서 재검증합니다. 이전 상태의 결과를 새 상태의 검증으로 보고하지 않습니다.
6. [공유 쉘](../../assets/report/report-shell.html)과 [코드 리뷰 리포트 본문](../../assets/report/code-review-report.html.template)으로 HTML 리포트를 작성하고, 가능하다면 리포트를 열고 경로를 출력합니다.
7. 터미널에는 짧은 요약만 남깁니다.

HTML 리포트를 터미널 요약보다 먼저 작성합니다. 긴 리뷰가 터미널 scroll에만 남거나 요약 직후 작업이 중단되어 결과물이 사라지는 상황을 막기 위한 순서입니다.

### 독립 탐색

subagent를 쓸 수 있고 이번 diff에 적용되는 관점이 셋 이상이면 절차 3의 조사를 나눕니다. 관점 수와 worker 수를 맞출 필요는 없습니다. 같은 문맥을 읽는 관점은 묶되 담당 관점과 누락 여부를 확인합니다. 최초 탐색에는 다른 worker의 잠정 결론을 전달하지 않습니다.

worker에게 확정한 commit SHA와 범위, 작업 트리 상태 식별값, 담당 관점, 공통 제약과 기준 문서를 전달합니다. worker는 조사한 상태가 일치하는지 확인하고 다음 형식으로 후보를 반환합니다. 명령 정책은 worker에도 그대로 적용됩니다.

- 담당 관점과 조사 범위, 확인하지 못한 범위
- `file:line`, 코드 스니펫, 위반한 규칙 링크 또는 실패 시나리오
- 판단에 필요한 전제, 확인한 방어 장치나 반례, 실행한 검증과 결과
- 제안이 있으면 잠정 제안과 영향을 받는 동작·계약, 다른 관점의 확인이 필요한 질문

subagent를 사용할 수 없으면 같은 절차를 순차 수행합니다. 자체 재검증을 독립 검증으로 표기하지 않습니다. 읽기 전용 작업자에게 수정 기능을 주지 않습니다.

### 후보 검증과 상충 조정

중앙 리뷰어가 지적 확정, 중복 병합, severity, 리포트를 담당합니다. 후보가 현재 변경에서 성립하는지, 기존 방어 장치나 문서의 예외가 주장을 반박하는지 확인합니다. 근거 계약을 만족하지 못한 후보는 확정 지적에서 제외합니다. 영향이 크거나 사실 판단이 엇갈린 후보는 가능하면 최초 발견자와 다른 검증자가 확인합니다.

같은 근본 원인의 지적은 하나로 합치고 관련 관점을 함께 적습니다. 같은 줄을 지적하더라도 실패 조건이나 해결해야 할 제약이 다르면 별개로 남깁니다. 후보마다 반복한 조사량이나 동의한 worker 수는 severity의 근거가 아닙니다.

| 관계 | 판단 방법 |
| --- | --- |
| 사실 판단이 다름 | 같은 코드 상태에서 실행 경로, 실패 조건, 반례를 대조합니다. 확인할 수 없으면 검증 한계로 남깁니다. |
| 적용 규칙이 충돌해 보임 | 규칙의 범위·예외와 명시된 우선순위를 확인합니다. 문서로 해소되지 않는 충돌은 결정 필요 사항으로 남깁니다. |
| 문제는 모두 사실이나 제안이 상충함 | 각 문제를 보존하고 두 제약을 함께 만족하는 대안을 검토합니다. 양립하지 않는 안을 동시에 권하지 않습니다. |
| 한 판단이 다른 판단의 전제임 | 선행 근거를 전달해 관련 관점만 후속 검토합니다. 전제가 미확정이면 후속 결론도 확정하지 않습니다. |

문제와 제안은 따로 판정합니다. 제안이 부적절해도 검증된 결함을 지우지 않습니다. 관점의 고정 우선순위나 다수결로 해결책을 고르지 않으며, 최종 권고들을 함께 적용할 때 다른 확인된 제약을 깨는지도 검토합니다. Severity는 확인된 영향과 발생 조건으로 정하고, 확신이 부족한 후보를 낮은 severity로 대신 보고하지 않습니다.

### 필요한 후속 검토

전체 관점을 다시 실행하지 않고, 선행 판단으로 질문이 달라진 관점만 검토합니다.

| 선행 결과 | 후속 검토 |
| --- | --- |
| 구체적인 실패 시나리오 | 관점 6과 11이 해당 실패를 잡는 테스트의 존재와 단언을 함께 확인합니다. 변경되지 않은 테스트도 근거로 인용했다면 포함합니다. |
| 경계·책임·호환성 계약의 해석 | 그 해석에 의존한 구현 판단과 관점 5의 문서 동기화를 재확인합니다. |
| 다른 동작에 영향을 주는 잠정 제안 | 관련 관점이 제안과 기존 제약의 양립 여부를 확인합니다. 예를 들어 UI 변경 제안은 접근성·포인터 동작 제약을 함께 확인합니다. |

후속 검토에는 관련 후보, 확정한 사실, 반대 근거와 답해야 할 질문을 전달합니다. 기본 한 차례 수행하고 새 근거로 판단이 달라질 때만 추가합니다. 정책 선택이나 환경 부재 때문에 남는 문제는 결정 필요 사항 또는 검증 한계로 보고하며 같은 질문을 반복하지 않습니다. 적용하지 않은 제안을 현재 구현으로 가정하거나 수정 후 검증을 완료했다고 적지 않습니다.

## 대규모 diff의 단계 하향

diff가 한 세션에서 읽기 어려운 규모면 관점 축 하나로는 나누어지지 않습니다. 관점 worker마다 전체 diff를 다시 읽어야 하기 때문입니다. 이때는 스코프 축을 하나 더 두고 단계로 나눠 내려갑니다.

스코프는 파일 수가 아니라 **변경 테마**로 자릅니다. 구조 변경, 디자인 시스템, 기능 화면처럼 되돌릴 수 있는 단위와 일치시켜야 리뷰 결과를 그대로 공유 단위로 옮길 수 있습니다. 디렉터리나 layer로 자르면 기능 하나가 여러 레이어에 흩어져 맥락이 끊깁니다.

단계 순서는 **blast radius**로 정합니다. 파일이 많은 스코프가 아니라 번지는 범위가 넓은 스코프를 먼저 봅니다. 공유 모듈의 결함 하나는 모든 화면에 퍼지지만 한 페이지의 결함은 그 페이지에서 끝납니다.

관점은 전역과 스코프로 가릅니다.

- 전역 관점은 전체 diff에 한 번만 돕니다. 관점 3(경계), 5(문서 동기화), 9(계측)가 여기 해당합니다. 셋 다 판단에 전체 그림이 필요해서, 스코프로 쪼개면 각 worker가 답할 수 없습니다.
- 나머지 관점은 스코프별로 돌리되 폭을 blast radius에 맞춥니다. 반경이 큰 스코프에서만 적용 가능한 관점을 모두 펼치고, 반경이 없는 스코프는 한둘로 좁힙니다.

단계 사이에서는 코드를 수정하지 않습니다. 확정된 사실, 공통 원인, 미해결 전제를 다음 스코프에 전달합니다. 아래 스코프도 같은 코드 상태에서 검토하고, 같은 원인의 영향은 기존 지적에 연결합니다. 전역 판단과 후속 스코프의 근거가 충돌하면 관련 판단을 다시 확인합니다.

단계마다 리포트를 남기되 전체 결과를 합칠 때 스코프 간 중복과 상충을 다시 확인합니다. 여러 단계에 걸친 진행 상태는 프로젝트의 백로그 문서가 소유합니다.

### 수정 후 재리뷰

수정은 사용자가 별도로 요청한 구현 작업에서 수행합니다. 리뷰는 검증된 지적과 제안을 보고하고 끝냅니다.

사용자가 수정 후 재리뷰를 요청하면 새 코드 상태를 기록하고 이전 리뷰와의 변경분을 확인합니다. 수정된 지적, 관련 호출 경로와 공유 제약을 우선 검토하며 영향 범위가 넓어진 경우 조사 범위를 확장합니다. 근거가 그대로인 지적은 다시 만들지 않고 기존 ID로 연결합니다. 기존 결함의 해소 여부와 새 회귀를 구분해 보고합니다.

## 명령 정책

문제를 새로 찾으려고 전체 check suite를 실행하지 않습니다. CI가 담당하는 검사를 반복하면 리뷰 신호가 약해집니다.

이미 찾은 지적 사항을 검증하는 명령은 실행해야 합니다. 런타임 동작 주장에는 측정 근거가 필요하고, 테스트 공백 주장도 관련 테스트를 직접 확인하면 더 강해집니다. 단일 테스트 파일이나 근거를 얻을 단일 명령처럼 좁은 범위로 실행합니다.

전체 검사를 대신 실행하지 말고 사용자가 아직 실행해야 하는 검사를 리포트에 남깁니다. 그 명령은 프로필이 정합니다.

## 지적 사항 보고 형식

결과 화면에는 중요도, 문제 제목, 짧은 파일 위치와 문제·제안을 표시합니다. 파일명만으로 모호하면 구분에 필요한 상위 경로를 덧붙이고 전체 파일로 연결합니다. 고정 ID와 관점은 상세 근거 안에 두며 관점 번호와 별도 표시 번호는 노출하지 않습니다.

본문은 문제와 제안 두 구획으로 나눕니다.

- **문제**: 실패 조건과 영향을 설명하고 판단에 필요한 근거·한계를 짧게 요약합니다. 상세 코드, 반례, 규칙 링크와 측정 출력은 해당 지적의 `코드·재현 근거`에 기본 접힘으로 둡니다.
- **제안**: 어떻게 고칠 수 있는지 설명하고, 구체적인 안이 검토됐으면 제안 코드를 상세 근거에 구분해 둡니다. 해결 방향이 미정이면 충돌하는 제약과 필요한 결정을 적습니다. 적용하거나 실행 검증하지 않은 제안은 그 한계를 밝힙니다.

제안이 둘 이상이면 제안마다 제목, 설명, 얻는 것과 잃는 것을 기재합니다. 검토한 구체적인 코드가 있으면 함께 둡니다. 트레이드오프를 적지 않으면 사용자가 무엇을 근거로 고를지 알 수 없습니다. 어느 방안을 권하는지 판단이 서면 문제 구획이나 제안 뒤 문장으로 밝힙니다.

결정 필요 사항은 선택지·영향·필요한 답을 적고, 검증 한계는 확인하지 못한 주장·이유·다음 확인 방법을 적습니다. 둘 다 확정 지적의 개수에 넣지 않습니다. 검증된 결함의 해결책만 미정이면 결함은 본문에 두고 결정 필요 사항에서 ID로 참조합니다. 근거 없는 가능성을 검증 한계 목록으로 옮겨 늘리지 않습니다.

지적 사항이 없으면 없다고 명시합니다. 리뷰가 길어 보이도록 항목을 채우지 않습니다.

정렬, severity 값, 검증 기록, 마크업은 아래 [HTML 리포트 계약](#html-리포트-계약)이 정합니다.

## HTML 리포트 계약

전체 리포트는 프로필이 정한 리포트 디렉터리에 저장합니다. 파일명은 branch 이름의 `/`를 `-`로 바꾸고, 기본 범위가 아니면 무엇으로 좁혔는지 짧은 라벨을 덧붙입니다. 범위 문자열을 그대로 쓰지 않습니다. `...`과 `/`가 들어가 파일명으로 쓸 수 없고, 경로로 좁힌 리뷰를 나타내지도 못합니다.

```text
<report-dir>/feat-tutoring-mode.html                    # 기본 범위
<report-dir>/feat-attendance-point-ui-attendance.html   # 경로로 좁힌 범위
```

사용자가 요약만 요청했거나 표시할 화면이 없으면 브라우저로 열지 않습니다. 그 외에는 플랫폼에 맞는 명령으로 열고 생성한 경로를 알립니다.

```bash
open <report-dir>/<file>.html        # macOS
xdg-open <report-dir>/<file>.html    # Linux
```

리포트는 [공유 쉘](../../assets/report/report-shell.html)을 복사한 뒤 `BODY_STYLE`, `BODY`, `BODY_SCRIPT` 세 구간을 [코드 리뷰 리포트 본문](../../assets/report/code-review-report.html.template)의 내용으로 바꿔 만듭니다. 쉘 구간의 CSS와 스크립트는 고치지 않습니다. 레이아웃을 다시 꾸미지 않고 새 색이나 크기를 만들지 않습니다. 디자인 규칙과 그 이유는 [리포트 HTML 디자인](report-design.md)이 소유합니다.

본문은 `.code-review`로 감싸고 [코드 리뷰의 읽기 조판](report-design.md#코드-리뷰의-읽기-조판)을 따릅니다. 문제·권장 제안과 판단에 필요한 근거 요약은 펼쳐 두며 상세 코드와 재현 근거는 접습니다. 복수 제안의 조건·득실 비교가 필요하면 템플릿의 선택 표를 사용합니다.

생성된 리포트는 다음 계약을 지켜야 합니다.

- `{{TITLE}}`에는 HTML document title을 넣습니다. `{{KICKER}}`는 `Code Review`이고 `{{HEADING}}`은 리뷰 대상 제목입니다. 표제 아래 메타 행은 생략하고 브랜치·짧은 revision 범위·파일 수·검토일은 검증 기록에 둡니다.
- 탭은 `리뷰 결과`와 `검증 기록` 두 개이며 처음에는 리뷰 결과를 표시합니다. 결과 탭의 개수는 확정 지적 수와 일치해야 합니다. 검증 기록은 선택했을 때만 보이며, 탭 밖에는 표제 외의 리뷰 내용을 두지 않습니다.
- 결과에는 `high`, `mid`, `low` 순으로 모든 지적을 표시합니다. 각 지적의 중요도를 화면과 인쇄에서 항상 보여 주고 `article`의 `data-sev`와 `.sev`의 `data-l`을 맞춥니다. 중요도별 필터나 번호는 만들지 않습니다.
- `F-001` 형태의 고정 ID는 `article`의 `id`와 상세 근거에 둡니다. 같은 리뷰의 단계·재리뷰에서 유지하며 severity가 바뀌어도 다시 매기지 않습니다. 병합한 ID의 대응은 내부 기록에 남깁니다. 독자에게 관련 지적을 연결할 때는 문제 제목을 링크 문구로 씁니다.
- 지적이 없으면 결과 화면에 검증된 지적이 없다는 문장을 둡니다. 사용자의 결정이 필요한 사항은 결과에 별도로 표시하고 확정 지적 개수에는 넣지 않습니다. 없다는 사실을 위한 빈 절은 만들지 않습니다.
- 탭은 ARIA tab·tabpanel 연결과 방향키·Home·End 이동을 지원합니다. JavaScript가 없으면 두 구획을 모두 읽을 수 있어야 하고 인쇄에서도 두 구획을 모두 표시합니다.
- 각 지적 사항은 문제·제안과 접힌 상세 근거를 유지합니다. 근거를 접어도 현재 결함과 테스트 공백, 확인된 사실과 미검증 제안을 구분할 수 있어야 합니다.
- 코드 스니펫은 `<pre data-hl="...">`에 1부터 센 줄 번호로 강조 위치를 지정하고 `<code class="language-...">`에 언어를 적습니다. 여러 줄은 `data-hl="4,5"`처럼 쉼표로만 잇습니다. 본문 텍스트는 HTML로 이스케이프합니다.
- 측정 출력은 코드 스니펫이 아니라 `pre.out`에 둡니다. 근거 코드와 실행 결과를 같은 모양으로 두면 무엇이 소스인지 구분되지 않습니다. 순서는 논증 순서를 따릅니다. 코드를 보고 문제를 짚었으면 코드가 먼저이고, 측정이 문제를 드러냈으면 출력이 먼저입니다.
- 검증 기록에는 실행한 검사와 결과, 검증 한계, 의미 있는 후보의 제외 이유, 계측 대조와 적용하지 않은 관점의 이유를 간결하게 적습니다. 이미 결과에 쓴 제안이나 수행 내역을 후속 조치로 반복하지 않습니다.
- 검증 기록은 검토 범위, 검증 결과, 제외 항목, 검토 관점 순으로 읽습니다. 범위는 짧은 정의 목록으로, 검증 결과는 상태·검사 이름·결과를 나눈 행으로 표시합니다. 상태는 실제 결과를 글자로 적고 미실행을 성공처럼 표현하지 않습니다. 미확인 범위와 판단 한계는 접지 않습니다. 제외 후보는 이름과 제외 결론을 펼침 제목에 쓰고 상세 근거를 접습니다. 계측 결론과 미확인 범위는 바로 표시하되 경로 대조와 관점별 제외 이유는 접을 수 있습니다.
- 전체 SHA·내용 해시·작업 트리 목록·worker별 진행 기록은 내부 조사 기록에만 보존하고 HTML에는 넣지 않습니다. 파일로 보존해야 하면 리포트 디렉터리의 별도 근거 자료로 두고 기본 화면에 노출하지 않습니다. 이 표시 제한은 코드 상태를 고정·대조하는 절차를 생략하는 근거가 아닙니다.
- 반복 block을 확장한 뒤 example row, 적용되지 않는 slot, placeholder text, 반복 안내 comment를 모두 제거합니다.

터미널 요약은 짧게 유지하고 상세 내용은 HTML 리포트에 둡니다.

## 검증

리포트를 저장하기 직전에 [리포트 HTML 디자인의 검증](report-design.md#검증)이 정한 세 가지를 실행합니다. 외부 참조가 없는지, 쉘 구간이 그대로인지, 본문 구간에 색 리터럴이 없는지입니다.

이어서 리포트 내용을 확인합니다. 결과 탭의 지적 사항 수와 본문의 일치, severity 값, 고정 ID의 유일성과 참조 대상의 존재, 문제·제안 구획과 상세 근거의 존재, 남은 slot과 반복 comment입니다. 결정 필요 사항과 검증 한계가 확정 지적 개수에 섞이지 않았는지도 확인합니다.

템플릿이나 공유 조판을 바꿨으면 실제 쉘로 조립한 샘플에서 light·dark, 393px와 데스크톱 폭을 확인합니다. 기본 결과 표시와 검증 기록 전환, 탭 방향키 이동, 키보드로 접힌 근거 열기, 테마 전환, JavaScript 비활성 상태와 인쇄 시 두 구획의 표시를 확인하고 페이지 전체에 가로 넘침이 없는지 측정합니다.

본문 문체와 용어는 [산문 문체 기준](prose-style.md)을 따르고, 리포트 전용 차이는 [리포트 HTML 디자인의 문체](report-design.md#문체)를 따릅니다. 저장 전에 두 기준으로 한 번 훑습니다.

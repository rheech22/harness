# 커밋 메시지 작성 기준

## 적용 범위

사람과 에이전트가 만드는 저장소의 모든 커밋에 적용합니다. 자동 실행기가 만드는 커밋도 이 형식을 따르며, 실행기 전용 대체 규칙이 있으면 그 실행기의 문서가 소유합니다. merge 커밋과 릴리스 도구가 만드는 버전 커밋은 형식 예외입니다.

이 문서는 형식과 판단 기준을 정하고 프로젝트마다 달라지는 값은 정하지 않습니다. scope 목록과 이슈 참조 형식은 [프로젝트 프로필](profiles/commit-messages.default.md)이 정합니다. 프로젝트에 프로필이 없으면 기본값을 씁니다.

## 규칙

### 제목

형식은 `type(scope): subject`입니다.

| type | 쓰는 경우 |
| --- | --- |
| `feat` | 사용자나 호출자가 볼 수 있는 동작을 추가하거나 바꿉니다. 화면 모양 변경을 포함합니다. |
| `fix` | 의도와 다르게 동작하던 것을 고칩니다. |
| `refactor` | 동작을 유지한 채 구조를 바꿉니다. |
| `perf` | 동작을 유지한 채 속도나 자원 사용을 개선합니다. |
| `test` | 테스트만 추가하거나 바꿉니다. |
| `docs` | 문서만 바꿉니다. |
| `ci` | CI workflow와 배포 자동화를 바꿉니다. |
| `chore` | 위에 해당하지 않는 유지 작업입니다. 포매팅, 의존성 갱신, 생성 파일 갱신이 여기 해당합니다. |

scope 목록은 프로젝트 프로필이 정합니다. 프로필의 [scope 목록](profiles/commit-messages.default.md#scope-목록)을 읽고 그 안에서 고릅니다.

- scope는 변경 이유가 속한 영역 하나를 씁니다. 문서 종류는 경로에 드러나므로 scope로 쓰지 않습니다. 여러 영역이 섞여 하나를 고를 수 없으면 커밋을 나눕니다.
- subject는 무엇을 바꾸는지 드러내는 한국어 한다체 한 문장입니다. 마침표를 찍지 않고 72자를 넘기지 않습니다. code identifier와 고유명사는 영어를 유지합니다.

### 본문

제목과 diff만 읽은 사람이 "왜 이렇게 했지?"라고 물을 수 있으면 본문을 씁니다.

- 쓰는 경우: 원인이 diff에 드러나지 않는 수정, 대안 중 하나를 고른 변경, 우회책과 임시 변경, 겉보기와 의도가 다른 테스트 변경, 조사 결과 고치지 않기로 한 판단이 담긴 변경
- 생략하는 경우: 제목이 이유까지 담는 변경, 오타·포매팅·이름 변경·생성 파일 갱신, 리뷰 지적을 그대로 반영한 문구 수정

해당하는 항목만 다음 순서로 씁니다.

1. 문제나 배경: 무엇이 잘못됐거나 왜 필요했는지
2. 이 방법을 고른 이유: 기각한 대안이 있으면 한 줄로
3. 확인한 것: 재현, 변이 테스트, 측정처럼 판단을 뒷받침한 검증
4. 종료 조건: 임시 변경이면 "…할 때까지 유지한다"

- diff를 다시 서술하지 않습니다. 파일별 변경 목록을 쓰지 않습니다.
- 한다체로 쓰고 72자 안팎에서 줄을 바꿉니다.
- 이슈 참조는 프로필의 [이슈 참조 형식](profiles/commit-messages.default.md#이슈-참조-형식)을 따라 본문 마지막에 두고, 런타임이 요구하는 `Co-Authored-By` trailer를 그 뒤에 둡니다.

### 이유의 근거

본문의 "왜"는 확인한 출처가 있을 때만 씁니다. 출처는 작업 중 직접 확인한 코드·로그·테스트 결과·문서, 사용자가 말한 이유나 결정, 링크할 수 있는 이슈나 문서입니다.

- 출처가 없는 이유는 쓰지 않습니다. 이유를 모르면 본문을 비웁니다.
- 확인하지 못한 판단은 추정으로 표시합니다. 예: "재현하지 못했고 코드 경로로 추정한다".
- 사용자 결정에서 나온 이유는 그렇다고 밝힙니다. 예: "사용자 합의에 따라 …". 에이전트가 그 결정을 자기 판단처럼 정당화하지 않습니다.
- 프로젝트 루트 `AGENTS.md`의 커밋 줄은 이 절을 에이전트에게 전달하는 요약입니다. 두 곳이 어긋나면 이 절이 기준입니다.

### 커밋 단위

- 한 커밋에는 변경 이유 하나를 담습니다. 리팩터링과 기능 변경을 나누는 기준은 [코딩 스타일](code-style.md#변경을-쉽게-만든-뒤-변경한다)을 따릅니다.
- 리뷰가 시작된 뒤에는 amend나 squash로 이력을 고치지 않고 지적 사안별로 새 커밋을 만듭니다.

## 이유

제목 형식을 고정하면 `git log`에서 type과 영역으로 변경을 찾을 수 있습니다. scope를 영역 하나로 닫는 이유는 같은 변경이 `docs(backlog)`와 `docs(docs)`처럼 다른 이름으로 흩어지지 않게 하기 위해서입니다.

본문은 diff로 복원할 수 없는 "왜"를 남기는 자리입니다. 반대로 지어낸 이유는 사실처럼 남아 이후 판단을 오도하므로, 이유가 없는 본문보다 해롭습니다. 에이전트는 변경의 배경을 모두 알지 못한 채 그럴듯한 이유를 만들기 쉬워 근거 규칙을 따로 둡니다.

리뷰 뒤에 이력을 고치면 리뷰어가 무엇이 바뀌었는지 커밋 단위로 따라갈 수 없습니다.

## 예외

- merge 커밋과 릴리스 도구의 버전 커밋은 형식을 따르지 않습니다.
- 리뷰 전의 로컬 브랜치는 amend와 squash로 정리할 수 있습니다.

## 검증

커밋 메시지를 검사하는 hook은 없으며 리뷰에서 확인합니다.

이 문서는 항상 로드되는 계층으로 전달합니다. 커밋은 특정 경로와 묶이지 않고 코드를 바꾸는 작업 대부분이 커밋으로 끝나기 때문입니다. 각 런타임이 어떤 수단으로 항상 로드하는지는 런타임 어댑터가 정합니다. 근거 규칙은 로딩 수단이 약한 런타임에서도 주입이 보장되도록 프로젝트 루트 `AGENTS.md`에 요약을 둡니다.

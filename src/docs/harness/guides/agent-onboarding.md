# 에이전트를 통한 하네스 도입

## 언제 쓰는가

사용자가 코딩 에이전트에게 이 하네스를 새 머신에 설치하거나 기존 설정과 함께 도입해 달라고 요청할 때 따릅니다. dotfiles는 필요하지 않습니다. 명령과 파일 형식의 기준은 [설치와 로컬 설정](setup.md)이 소유하고, 이 문서는 에이전트의 조사·판단·적용·보고 순서를 정의합니다.

사용자는 다음처럼 요청할 수 있습니다.

> 이 저장소의 에이전트 도입 가이드를 따라 현재 머신에 하네스를 설치하고 적용해 줘. 기존 설정과 다른 플러그인의 훅은 보존하고, 충돌하는 값이 있으면 해당 항목만 물어봐 줘.

사용자가 적용까지 요청했다면 승인된 범위 안에서 진행합니다. 동일한 적용 의사를 반복해서 확인하지 않습니다. 특정 값을 고를 정보가 없거나 기존 설정과 충돌할 때 필요한 선택만 묻습니다. 미리보기만 요청했다면 적용하지 않습니다. 설치 요청에 포함되지 않은 다른 저장소의 원본이나 앱의 세션·기록은 삭제하지 않습니다.

## 절차

### 1. 범위와 현재 상태 확인

사용할 런타임과 스킬 프로필, 체크아웃 위치를 확인합니다. 이미 요청이나 환경에서 확인한 값은 다시 묻지 않습니다. 설치된 런타임을 확인할 때와 원하는 런타임을 결정할 때를 구분하며, 설치되어 있다는 이유만으로 모두 적용하지 않습니다.

Git, Node.js 22.19 이상, `npx`와 필요한 런타임 CLI를 확인합니다. 추가 CLI는 선택한 스킬과 `harness.json`의 `tools`를 기준으로 준비합니다. 필요하지 않은 프로그램을 한꺼번에 설치하지 않습니다. Claude·Codex 실행 파일은 이미 설치되어 있을 수 있으며, 이 하네스가 프로그램 설치를 위해 dotfiles를 호출하지는 않습니다.

체크아웃이 있다면 `git status --short`와 원격 주소부터 확인합니다. 미커밋 변경을 덮어쓰거나 `reset --hard`하지 않습니다. 새로 clone할 때는 빈 위치를 사용하며 `~/harness` 같은 고정 위치를 전제하지 않습니다.

선택한 어댑터의 `adapter.json`에서 대상 경로를 읽습니다. 기존 지침·스킬·설정 파일이 없는지, 일반 파일인지, 다른 저장소를 가리키는 symlink인지 확인합니다. 같은 이름의 기존 스킬과 프로젝트별 공통 훅 등록도 확인합니다. 설정의 키·종류·연결 대상을 중심으로 조사하고 credential이나 전체 설정 내용을 보고서·로그에 출력하지 않습니다.

### 2. 원본과 설치 결과 준비

[설치와 로컬 설정](setup.md)의 순서로 custom을 build하고 필요한 external을 설치한 뒤 `check`를 실행합니다. external 설치는 스킬 파일을 가져오는 작업이며, 해당 스킬이 사용하는 CLI 설치와는 별개입니다.

`dist/`를 직접 편집하지 않습니다. 하네스를 도입하기 위해 사용자 프로젝트의 코드나 문서 구조를 재작성하지 않습니다. 프로필 선택과 기존 설정 적용으로 해결하고, 하네스 기본값을 바꿀 필요가 있다면 그 변경을 별도로 설명합니다.

### 3. 두 적용 계획을 먼저 확인

하네스 체크아웃에서 `link`와 `configure`를 모두 적용 옵션 없이 실행합니다. 아래는 Claude와 common·writing 프로필을 선택한 경우의 예시이며, 실제로 확인한 런타임·프로필로 바꿔 실행합니다.

```bash
node scripts/link.mjs --profile common,writing --runtime claude
node scripts/configure.mjs --runtime claude
```

`link`는 지침·스킬·규칙의 symlink를 계획하고, `configure`는 설정과 훅의 관리 항목을 계획합니다. 다른 파일을 가리키는 기존 링크를 `link --apply`가 자동으로 교체해 주지는 않습니다. 설정 계획에 오류가 없더라도 링크 계획의 모든 대상과 기존 파일의 충돌을 확인한 뒤 적용합니다.

| 기존 상태 | 처리 |
| --- | --- |
| 설정 파일 없음 | 새 로컬 파일 생성 계획을 확인합니다. |
| 기존 일반 파일, 관리 항목이 겹치지 않음 | 기존 항목을 보존하는 추가 계획을 확인합니다. |
| 설정 값 또는 관리 훅 충돌 | 적용을 멈추고 해당 선택만 사용자에게 묻습니다. |
| settings가 symlink | 이관 범위와 대상을 확인하고 `--adopt-symlink`로 다시 계획합니다. |
| 이미 하네스 적용됨 | 관리 기록을 보존하고 변경 계획만 확인합니다. |
| 관리 기록이 손상됨 | 적용을 멈추고 백업과 파일을 조사합니다. 기록 삭제로 우회하지 않습니다. |

### 4. 충돌을 해결할 때 지켜야 할 기준

일반 설정 값뿐 아니라 이전에 관리한 훅의 command·옵션·matcher가 바뀌거나 훅이 삭제된 경우에도 충돌할 수 있습니다. 처음 도입할 때 같은 이벤트·matcher·명령이 다른 옵션으로 존재해도 충돌입니다. 어떤 항목의 후속인지 명확하지 않은 상태에서 새 훅을 덧붙이지 않습니다.

사용자에게는 항목의 역할과 선택이 바꾸는 동작을 설명합니다. 예를 들어 timeout은 다음처럼 물을 수 있습니다.

> 배포물 수정 감지 훅의 timeout이 로컬에서는 10초, 하네스에서는 5초입니다. 10초를 유지할까요, 하네스의 5초를 적용할까요?

로컬 값을 유지하려면 승인된 의도를 하네스 원본에도 반영하거나, 해당 선언을 제거해 관리 대상에서 해제하는 방법을 검토합니다. 공유 원본에 머신별 경로나 credential을 넣지 않습니다. 원본에서 관리 선언만 제거하는 경우 로컬에서 변경한 항목은 보존되지만, 변경되지 않은 이전 관리 값은 제거될 수 있으므로 계획을 확인합니다.

하네스 값을 적용하기로 했다면 먼저 설정과 관리 기록을 백업합니다. 기존 관리 기록이 있으면 충돌한 로컬 항목만 이전 관리 값으로 되돌린 뒤 `configure`를 다시 계획합니다. 처음 도입하는 경우에는 승인된 충돌 항목만 원본의 의도와 맞춘 뒤 다시 계획합니다. 명령의 경로 토큰은 실제 체크아웃 경로로 변환해야 하며 원본의 `{{skillDistributionGuard}}`를 로컬 설정에 그대로 넣지 않습니다.

충돌 메시지의 배열 위치는 하네스의 선언 또는 이전 관리 기록에서 나온 위치입니다. 외부 훅 때문에 로컬 배열 순서가 다를 수 있으므로 같은 인덱스를 무조건 수정하지 말고 이벤트·matcher·명령과 이전 관리 기록을 대조합니다.

외부 플러그인의 훅을 삭제하거나 관리 기록을 비워 충돌을 통과시키지 않습니다. 원본에 선언이 남아 있는 관리 훅의 로컬 삭제도 의도적인 변경으로 취급합니다. 사용자가 그 훅을 원하지 않는다면 선언에서 제거하는 선택을 설명합니다.

### 5. 백업 후 적용

기존 지침·스킬 링크의 충돌을 해결할 때는 해당 파일·링크만 저장소 밖에 백업합니다. 다른 플러그인이 사용하는 디렉터리 전체를 옮기거나 삭제하지 않습니다. settings의 symlink 이관은 `configure --adopt-symlink --apply`를 사용하고 기존 대상 파일을 유지합니다.

계획이 정리되면 선택한 범위의 `link --apply`와 `configure --apply`를 실행합니다. 적용 결과와 백업 위치를 기록합니다. `configure`는 런타임별로 백업·복구하므로 여러 런타임을 선택했다면 각 결과를 확인합니다.

dotfiles 등 이전 관리 도구가 같은 경로를 계속 배포한다면 재적용 시 충돌이 돌아옵니다. 이전 저장소 정리까지 요청받았다면 해당 배포 선언을 함께 제거하고, 그렇지 않으면 남은 소유권 충돌을 보고합니다. 인증·세션·캐시는 이관 대상으로 취급하지 않습니다.

기존 프로젝트에 사용자 범위 공통 훅이 복사되어 있다면 전역 등록이 동작하는 것을 확인한 뒤 중복 등록만 정리합니다. 프로젝트 전용 훅·MCP·지침·프로필은 유지합니다. 단순 사용자 범위 설치를 위해 모든 프로젝트에 `init-project`를 실행하지 않습니다.

## 검증

다음 항목을 실제로 확인합니다.

- `check`가 통과하고 `link` 재적용이 새 링크를 만들지 않습니다. 다른 기존 파일을 건드리지 않았는지도 확인합니다.
- `configure` 재계획에서 `changes`가 비고 `stateUpdate`가 false입니다. 관리하지 않는 설정과 외부 훅은 도입 전과 같습니다.
- 로컬 settings는 일반 파일이고 훅 명령은 실제 체크아웃을 가리킵니다. 설정 원본에 머신별 절대 경로가 기록되지 않았습니다.
- 새 세션의 로딩과 훅 신뢰 절차는 각 어댑터 README와 [런타임 로딩 검증](verification.md)을 따릅니다. 확인하지 못한 런타임·인증·신뢰 단계는 미검증으로 남깁니다. 파일 연결 성공만으로 모델 로딩까지 확인했다고 보고하지 않습니다.
- 이전 관리 도구도 정리한 경우에는 격리 HOME에서 그 도구를 재적용해 하네스 파일이 바뀌지 않는지 확인합니다. 실제 머신에서 관계없는 설정 전체를 재적용하지 않습니다.

도입 결과에는 적용한 체크아웃·런타임·프로필, 변경한 대상, 보존한 설정, 백업 위치, 검증 결과와 남은 충돌·미검증 항목을 남깁니다. 커밋·push가 요청되지 않았다면 로컬 도입과 저장소 발행을 구분해 보고합니다.
